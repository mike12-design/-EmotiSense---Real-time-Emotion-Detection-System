一、模型与算法类
================================================================================

Q1：你为什么选择 YOLOv8 做人脸检测，而不是 MTCNN、RetinaFace 或 OpenCV Haar Cascade？
-------------------------------------------------------------------------------
- YOLOv8 是单阶段目标检测器，在速度与精度之间取得了较好的平衡，非常适合实时视频流场景
- 相比 Haar Cascade（论文中用于眼部检测的传统方法），YOLOv8 对光照变化、角度偏转更鲁棒
- 比 MTCNN 更快，且 Ultralytics 提供了统一的 Python API，集成方便
- 实际在 config.yaml 中配置了 frame_skip: 2（每隔 2 帧处理一次），进一步保证实时性

Q2：你的眼部微表情模型为什么选择 ResNet18，而不是 MobileNet 或 EfficientNet？
-------------------------------------------------------------------------------
- ResNet18 的残差连接可以有效解决深层网络的梯度消失问题，适合眼部这种细节特征提取
- 参数量适中（约 11M），训练和推理速度快，适合实时系统
- 论文中采用分层学习率微调：先在完整面部表情数据集上预训练，再在仅含 Sad/Neutral 的数据集上
  fine-tune，这种迁移学习策略在小样本眼部数据上效果显著
- 可以回答：如果进一步优化，MobileNetV3 可能是更好的轻量化选择，但 ResNet18 在精度上更优

Q3：你的多模型融合策略具体是怎么做的？三种融合方式的区别是什么？
-------------------------------------------------------------------------------
你的系统支持三种融合方式，在 config.yaml 中通过 detector_type 切换：

(1) 规则融合 (decision_fusion, k=0.5):
    - 手动设定权重 k：眼部模型占 50%，全局 HSEmotion 模型占 50%
    - 优点：可解释性强；缺点：k 值需要人工调参

(2) 眼睛融合 (eye_fusion):
    - 仅在 Sad/Neutral 情绪上融合眼部特征，其他情绪直通全局模型
    - 适合特定场景优化（如悲伤检测）

(3) 元学习器融合 (meta_learner):
    - 从 HSEmotion 全局模型提取 5 类情绪概率（Sad, Neutral, Angry, Happy, Surprise）
      加上眼部模型的 Sad 概率，拼接为 6 维特征向量
    - 送入经过训练的分类器（你的论文中对比了逻辑回归、SVM、随机森林、梯度提升树，
      最终选择了准确率最优的随机森林）
    - 优点：数据驱动，自动学习最优融合权重；不需要手动调 k 值
    - 论文数据显示：Sad/Neutral 二分类准确率从单一模型的 71.94% 提升至 72.80%

Q4：为什么元学习器最终选择随机森林，而不是更复杂神经网络？
-------------------------------------------------------------------------------
- 特征维度只有 6 维，数据量有限，复杂模型容易过拟合
- 随机森林在小样本、低维特征场景下泛化能力好
- 推理速度快（毫秒级），适合实时系统
- 可解释性比神经网络强——可以输出特征重要性，理解哪些特征贡献最大
- 训练简单，不需要 GPU，部署成本低

Q5：你如何解决情绪识别中的过拟合问题？
-------------------------------------------------------------------------------
- 数据增强：旋转、翻转、亮度调整等（OpenCV 预处理阶段）
- 迁移学习：ResNet18 使用 ImageNet 预训练权重 + 分层学习率微调
- K 折交叉验证训练眼部模型
- Dropout 和 Batch Normalization（ResNet18 自带）
- 情绪稳定器（滑动窗口多数投票）作为一种后处理正则化，抑制单帧误判

Q6：HSEmotion、DeepFace 和 FER 这三个模型各有什么优缺点？
-------------------------------------------------------------------------------
- DeepFace：最稳定可靠，支持多种后端（VGGFace、Facenet 等），但速度较慢，
  在你的系统中作为 fallback 和参考基准
- HSEmotion：速度快，专为情绪识别优化，但论文中提到有"模型兼容问题"，
  需要特定版本的依赖
- FER：轻量级，适合资源受限场景，但准确率相对较低
- 你的系统默认使用 HSEmotion + 眼部模型 + 元学习器融合，充分发挥各模型优势

Q7：FER2013 和 CK+ 数据集有什么局限性？你的训练数据如何弥补？
-------------------------------------------------------------------------------
- FER2013：规模大（约35k张）但标注噪声大，很多是互联网爬取的灰色低分辨率图片
- CK+：标注质量高但样本少（仅 593 个序列），且多为实验室受控环境
- 局限性共性：种族/年龄分布不均，多为正面光照、无遮挡
- 你的弥补措施：
  (1) 使用来自社交媒体 + IMDB + AffectNet 等多源融合数据集
  (2) 包含各种光照条件、不同种族的照片
  (3) 通过眼部局部特征提取，降低对全局光照的敏感度

二、系统架构与实现类
================================================================================

Q8：你的系统架构是什么？为什么选择前后端分离？
-------------------------------------------------------------------------------
- 三层架构：Vue 3（表示层）→ FastAPI（业务逻辑层）→ SQLite（数据层）
- 前后端分离的好处：
  (1) 前端通过浏览器直接调用摄像头（getUserMedia API），不需要安装客户端
  (2) 后端专注 AI 推理和数据处理，可以部署在 GPU 服务器上
  (3) 前后端独立开发、独立部署、独立扩展
  (4) REST API 接口标准化，方便未来对接移动端或其他终端

Q9：前后端之间如何进行实时通信？视频流如何传输？
-------------------------------------------------------------------------------
- REST API：用于登录、数据查询、资源管理等常规操作（约 50 个端点，见 api.py）
- MJPEG 流：`/video_feed` 端点通过 FastAPI 的 StreamingResponse 实时推送带标注的视频帧
- WebSocket（如果有的话）可用于更低延迟的双向通信
- 情绪检测轮询：前端定时调用 `/api/status` 获取当前情绪状态和干预信息

Q10：系统在实时性方面做了哪些优化？
-------------------------------------------------------------------------------
- frame_skip: 2（每隔 2 帧处理一次，FPS 30 时实际处理 15 帧/秒）
- detection_interval: 3.0 秒（情绪分析不是每帧都做，降低计算负载）
- YOLOv8 单阶段检测，速度快
- ResNet18 轻量级网络
- 情绪稳定器窗口仅 5 帧，延迟低
- SQLite 轻量数据库，读写快
- 多线程处理（视频采集与 AI 推理分离）

Q11：你的系统数据库为什么选择 SQLite 而不是 MySQL 或 PostgreSQL？
-------------------------------------------------------------------------------
- SQLite 是嵌入式数据库，不需要单独安装数据库服务器，部署简单
- 对于毕业设计/原型系统级别，并发量不高，SQLite 完全够用
- 数据量可控：论文中配置了 max_data_records: 1000，情绪记录有上限
- 方便迁移：整个数据库就是一个 .db 文件（你项目中的 emotisense.db）
- 如果未来需要高并发，可以升级到 PostgreSQL（FastAPI + SQLAlchemy 改配置即可）

Q12：你的系统如何处理"画面中无人脸"的情况？
-------------------------------------------------------------------------------
- YOLOv8 检测不到人脸时不报错，只返回空结果
- 情绪稳定器在无新预测时保持上次的稳定情绪
- 情绪动力学引擎的滑动窗口不会被无效数据污染
- 测试用例 002-05 已验证：画面中无人脸时系统正常运行，不进行错误识别

Q13：用户认证和权限管理是怎么实现的？
-------------------------------------------------------------------------------
- 前端：Vue Router 路由守卫（router/index.js），localStorage 存储登录状态
- 后端：基于角色的访问控制（admin/user 两种角色）
- 密码使用哈希存储（password_hash 字段），不存明文
- 管理员可访问：数据分析、用户管理、资源管理、系统日志
- 普通用户可访问：实时监控、历史统计、日记管理、个人设置
- 测试用例 001-04/004-06 验证了未授权访问会被拦截

三、情绪处理流程类
================================================================================

Q14：从摄像头拍到人脸到最终输出情绪结果，整个处理流程是怎样的？
-------------------------------------------------------------------------------
请梳理你的完整 Pipeline（这一定是高频问题）：

  摄像头采集 → OpenCV 预处理（缩放/颜色转换）→ frame_skip 跳帧
  → YOLOv8 人脸检测 → 人脸区域裁剪
  → 并行：(A) HSEmotion 全局情绪推理 (B) 眼部区域提取 + ResNet18 眼部模型推理
  → 元学习器融合（6维特征 → 随机森林分类器）
  → 情绪稳定器（滑动窗口多数投票，5帧窗口）
  → 情绪动力学引擎（效价计算 + 滑动窗口负情绪比例投票）
  → 触发干预决策（播放音乐/语音安慰）
  → 写入 SQLite（情绪日志表 + 系统事件表）
  → 前端实时展示

Q15：情绪稳定器（Stabilizer）和情绪动力学引擎（Dynamics）有什么区别？
-------------------------------------------------------------------------------
这是你的系统亮点，老师可能会深入追问：

情绪稳定器（stabilizer.py）：
- 作用：解决单帧情绪"闪烁"问题（例如连续 5 帧中 3 帧 sad、2 帧 neutral，输出 sad）
- 方法：维护一个固定大小的滑动窗口（默认 5 帧），统计众数
- 只有当某情绪在窗口中占比 ≥ 60% 时才切换输出，否则保持上次的稳定结果
- 类似于硬件按键的"去抖动"（debounce）

情绪动力学引擎（emotion_dynamics.py）：
- 作用：在更长时间尺度上判断用户是否持续处于负面情绪，决定是否触发干预
- 方法：
  (1) 效价映射：每种情绪映射为数值（happy=1.0, sad=-0.6, angry=-1.0...）
  (2) 情绪分数 EMA 平滑：mood_score = mood_score * 0.8 + current_valence * 0.2
  (3) 滑动窗口投票：20 帧窗口（约 100 秒），当负面情绪占比 ≥ 70% 时触发干预
  (4) 冷却时间：两次干预之间至少间隔 30 秒

两者的关系：稳定器负责短期去噪 → 动力学引擎负责长期趋势分析

Q16：为什么情绪动力学引擎的窗口大小选 20，负面比例阈值选 0.7？
-------------------------------------------------------------------------------
- 窗口大小 20：假设每 5 秒产生一个稳定情绪输出（detection_interval=3s + 处理时间），
  20 × 5 = 100 秒 ≈ 1.5 分钟。这个时间窗口足够长以滤除短暂的情绪波动，
  又不会太长导致干预响应太慢
- 负面比例 0.7：20 帧中需要至少 14 帧（70%）为负面情绪才触发。
  这个阈值在"敏感性"和"特异性"之间取得平衡
- 冷却时间 30 秒：防止连续重复干预，造成用户反感
- 这些都是经验参数，论文中可以说明是可调的

Q17：你的系统如何进行情绪干预？干预策略是什么？
-------------------------------------------------------------------------------
- 触发条件：情绪动力学引擎检测到持续负面情绪（负情绪窗口占比 ≥ 70%）
- 干预手段：
  (1) 音乐播放：根据当前情绪匹配情绪标签的音乐（如 sad 情绪播放舒缓音乐）
  (2) TTS 语音安慰：使用 edge-tts 将安抚文本转为语音播放
  (3) 治愈文案推送：匹配情绪标签的安慰话术
- 个性化优先级：用户个人音乐库/话术库 > 管理员全局资源库
- 干预记录：每次干预写入系统事件表，供后续分析

Q18：公共音乐和个人音乐、公共话术和个人话术之间是什么关系？
-------------------------------------------------------------------------------
- 全局资源库：由管理员维护，作为所有用户的默认资源池（fallback）
- 个人资源库：用户可上传/添加自己的音乐和话术
- 优先级：个人资源优先于全局资源
- 这种设计实现了"千人千面"的个性化干预

Q20：准确率只提升了不到 1 个百分点（71.94%→72.80%），这个提升有意义吗？
-------------------------------------------------------------------------------
这是一个老师可能会追问的尖锐问题，建议这样回答：

- Sad/Neutral 本身就是公认的"易混淆情绪对"，是人脸表情识别中的难点
  （Gorbova 等人的研究也专门讨论 hidden sadness 问题）
- 1% 的提升在易混淆情绪上是可观的，因为这两类的基线区分度本来就低
- 更重要的是：多模型融合提高了系统在复杂环境下的鲁棒性（光照、遮挡等），
  而不仅仅是准确率数值
- 如果老师进一步追问，可以说明：后续可以在更大规模数据集上验证，
  或引入更多模态（语音、文本）进一步提升

Q22：你的系统如何处理光照变化、遮挡和侧脸等挑战？
-------------------------------------------------------------------------------
- 训练数据包含多光照条件的样本
- YOLOv8 对姿态变化有一定鲁棒性
- OpenCV 预处理阶段可进行直方图均衡化等光照补偿
- 眼部局部模型在部分遮挡时（如口罩）仍可工作（只要眼睛可见）
- 情绪稳定器的去抖动机制可以过滤因遮挡导致的偶发误判
- 如果完全无法检测到人脸，系统静默等待，不输出错误结果

-------------------------------------------------------------------------------

- 测试用例包含了真实摄像头场景的功能验证
- 建议在答辩时准备一个实际演示视频，展示不同光照、不同表情下的识别效果

Q24：你的毕业设计相比已有工作，创新点在哪里？
-------------------------------------------------------------------------------
你的核心创新点（论文中已有体现）：

(1) 多模型决策融合架构：
    - 不是简单的模型集成，而是将全局人脸特征（HSEmotion）与局部眼部特征
      （ResNet18）结合，并通过元学习器（随机森林）进行数据驱动的融合
    - 专门针对 Sad/Neutral 易混淆情绪的优化

(2) "感知→分析→干预"闭环设计：
    - 大多数情绪识别系统只做到"识别"，你的系统做到了"识别→持续监测→智能干预"
    - 情绪稳定器 + 情绪动力学引擎的双层级联架构

(3) 个性化干预：
    - 支持用户自定义音乐库和话术库，实现千人千面的情绪关怀

(4) 完整的前后端全栈系统：
    - 不只是算法实验，而是可实际使用的 Web 应用
    - Vue 3 + FastAPI + SQLite，工程完整性高

Q25：你这个系统和市面上已有的情绪识别产品（如 Affectiva、Microsoft Azure 情绪 API）有什么区别？
-------------------------------------------------------------------------------
- 商业 API 是通用的情绪识别服务，你的系统是面向"情绪关怀"的垂直应用
- 你的系统包含了完整的干预闭环（音乐 + TTS + 话术），商业 API 通常只返回情绪标签
- 开源、可定制、可本地部署，数据隐私性好
- 针对 Sad/Neutral 混淆做专门优化，这种场景在心理健康领域非常重要

Q26：这个系统的实际应用价值是什么？
-------------------------------------------------------------------------------
- 心理健康辅助：对独居老人、远程患者进行情绪监测和及时安抚
- 智能陪伴：可集成到智能家居、陪伴机器人中
- 教育场景：监测学生学习状态，调整教学节奏
- 驾驶员状态监测：检测疲劳、路怒等危险情绪
- 远程心理治疗：辅助治疗师了解患者情绪变化趋势

Q28：你的系统在多用户/高并发场景下性能如何？有什么瓶颈？
-------------------------------------------------------------------------------
- 当前是单用户设计（一个摄像头对应一个用户），没有做多用户优化
- 瓶颈主要在：
  (1) 深度学习推理：每次情绪分析需要同时运行 HSEmotion + 眼部模型，GPU 可以加速
  (2) 摄像头资源：一个摄像头只能服务一个用户
  (3) SQLite 在并发写入时会锁库（单写多读）
- 改进方向：
  (1) 模型推理服务化（如 Triton Inference Server）
  (2) 数据库升级到 PostgreSQL
  (3) 使用 Redis 缓存热点数据

Q32：什么是元学习（Meta-Learning）？你系统中的"元学习器"和通常说的 MAML 有什么区别？
-------------------------------------------------------------------------------
- 你的"元学习器"（Meta-Learner）是指 Stacking（堆叠泛化/集成学习的一种），
  即用一个学习器来融合多个基学习器的输出
- 这与 MAML（Model-Agnostic Meta-Learning）等 few-shot 元学习不同
- 你的用法更接近于"学习如何融合"（Learning to Combine），而非"学习如何学习"
- Stacking 是集成学习中的经典方法，用在这里是合适的命名

Q33：你论文中提到的 Valence-Arousal 情绪模型是什么？你的效价映射（Valence Map）是怎么设计的？
-------------------------------------------------------------------------------
- Valence（效价）：情绪的正负程度（积极/消极）
- Arousal（唤醒度）：情绪的强烈程度（高/低）
- 你的系统主要使用一维效价值（Valence），映射表在 emotion_dynamics.py 中：
  happy=1.0, surprise=0.3, neutral=0.0, sad=-0.6, fear=-0.8, angry=-1.0, disgust=-0.9
- 这个映射参考了心理学中的情绪环形模型（Circumplex Model of Affect）
- 卡尔曼滤波（advanced_analyzer.py）用于平滑效价序列

Q34：你的卡尔曼滤波在情绪分析中具体是怎么用的？
-------------------------------------------------------------------------------
- 在 advanced_analyzer.py 中实现
- 将连续的情绪效价值视为含噪声的观测序列，用卡尔曼滤波估计"真实"的情绪状态
- 状态方程：假设情绪状态缓慢变化（随机游走模型）
- 观测方程：每次检测到的情绪效价值 = 真实情绪状态 + 观测噪声
- 卡尔曼增益自动权衡"模型预测"与"观测值"，结果更平滑、更有鲁棒性

Q44：Vue 3 的响应式原理是什么？为什么 Vue 3 用 Proxy 替代 Vue 2 的 Object.defineProperty？
-------------------------------------------------------------------------------
- Vue 2 的 Object.defineProperty 只能劫持对象已有的属性，无法检测属性的新增/删除，对数组的索引和 length变化也无法监听（需要 $set）
- Vue 3 使用 ES6 Proxy 代理整个对象，可以拦截属性的读取（get）、设置（set）、删除（deleteProperty）、in 操作符等 13 种操作
- Proxy 的性能更好，不需要递归遍历对象的每个属性
- 你的项目中使用 ref（基本类型）和 reactive（对象类型）来声明响应式数据
- 追问：ref 和 reactive 的区别？
  → ref 包装基本类型，通过 .value 访问，内部自动转为 {value: ...} 的 reactive 对象
  → reactive 用于对象，直接访问属性，但不能替换整个对象（会丢失响应式）

Q45：Vue 3 的 Composition API 和 Options API 有什么区别？你为什么用 Composition API？
-------------------------------------------------------------------------------
- Options API（Vue 2 方式）：按选项类型组织代码（data、methods、computed、watch），
  同一功能的逻辑分散在不同选项中，大型组件难以维护
- Composition API（Vue 3 新方式）：按功能逻辑组织代码，相关的数据、方法、计算属性
  写在一起，逻辑复用更容易（自定义 hooks）
- Composition API 更好的 TypeScript 支持
- setup 语法糖（<script setup>）更简洁，不需要手动 return
- 你的项目中 MonitorMode.vue 等组件使用了 Composition API

Q46：你的项目里用了哪些组件通信方式？各适用于什么场景？
-------------------------------------------------------------------------------
| 方式 | 方向 | 你的项目使用场景 |
|------|------|-----------------|
| props / emits | 父→子 / 子→父 | 父组件传配置给子组件，子组件通过 emit 通知父组件事件 |
| v-model | 双向绑定 | 表单输入（登录页面的用户名/密码） |
| provide / inject | 祖→孙 | 全局主题、用户信息传递（避免层层 props） |
| Pinia store | 全局共享 | 情绪状态（sensing.js store）、用户登录状态 |
| Vue Router | 路由参数 | 页面间传参（如跳转到用户详情页时传递 user_id） |

Q48：你的项目前端路由守卫（Vue Router）是怎么做权限控制的？

Q49：v-if 和 v-show 有什么区别？在情绪监控页面哪个更合适？
-------------------------------------------------------------------------------
- v-if：条件为假时完全不渲染 DOM（惰性），切换开销大，初始渲染开销小
- v-show：始终渲染，只是通过 CSS display:none 隐藏，切换开销小，初始渲染开销大
- 在情绪监控页面：
  → 干预弹窗/音乐播放器用 v-if（不干预时不占 DOM 资源）
  → 人脸检测框的显示/隐藏用 v-show（频繁切换）
  → 情绪标签切换用 v-show（避免频繁创建销毁 DOM）

Q50：v-html 指令有什么安全风险？如何在你的项目中防止 XSS？

- v-html 会将字符串作为 HTML 渲染，如果内容包含用户输入且未消毒，
  攻击者可以注入 <script> 标签或其他恶意 HTML（XSS 攻击）
- 在你的项目中：
  → 安慰话术内容是管理员从后台录入的，如果使用 v-html 展示，
    需要确保后端已过滤（或前端使用 DOMPurify 库净化）
  → 日记内容（用户输入）不能使用 v-html，应该用 {{ }} 文本插值（自动转义）
  → 建议所有用户生成的内容使用纯文本渲染，仅对可信源（如管理员录入的话术）
    使用 v-html，并配合 CSP（Content-Security-Policy）响应头

Q57：FastAPI 的 CORS 中间件是怎么配置的？你项目中 allow_origins=["*"] 有什么风险？
-------------------------------------------------------------------------------
- 你的项目在 main.py 中配置：
  app.add_middleware(CORSMiddleware, allow_origins=["*"], allow_credentials=True, allow_methods=["*"], allow_headers=["*"])
- allow_origins=["*"] 表示允许任何域名跨域访问，适合开发阶段
- 安全风险：生产环境中应指定具体的域名白名单，如 allow_origins=["https://myapp.com"]
- 此外，allow_origins=["*"] 与 allow_credentials=True 不能同时使用（浏览器安全限制）
  如果设置 allow_credentials=True，origin 必须指定具体域名
- 跨域的本质：浏览器同源策略（Same-Origin Policy）阻止了不同协议/域名/端口间的请求，
  CORS 是服务器声明愿意接受哪些跨域来源
- 预检请求（OPTIONS）：非简单请求（如 Content-Type: application/json 的 POST 请求）
  会先发送 OPTIONS 预检请求，CORSMiddleware 自动处理

追问：什么是简单请求和非简单请求？
  → 简单请求：GET、POST（Content-Type 为 form 或 text）、HEAD
  → 非简单请求：PUT、DELETE、Content-Type: application/json 的 POST、
    自定义 Header 等，需要先发 OPTIONS 预检

Q58：FastAPI 的依赖注入（Depends）是怎么工作的？你的项目中用到了吗？
-------------------------------------------------------------------------------
- 依赖注入的核心：用 Depends() 声明函数需要的依赖，FastAPI 在调用路由函数前
  自动解析并注入所需的资源
- 优点：
  → 代码复用：多个路由可以共享同一个依赖（如数据库会话、权限校验）
  → 可测试性：测试时可以轻松替换依赖（你的 tests/conftest.py 中使用了依赖覆写）
  → 自动级联：依赖可以依赖其他依赖，FastAPI 自动构建依赖树
- 你的项目中的使用场景：
  → get_db() 依赖：提供数据库连接，请求结束后自动关闭
  → get_current_user() 依赖：从 token 中解析当前用户，实现认证
  → 测试中的依赖覆写（dependency_overrides）：用假的依赖替换真实依赖

追问：依赖中使用 yield 的作用？
  → yield 前的代码在请求处理前执行（如打开数据库连接）
  → yield 后的代码在请求处理完成后执行（如关闭数据库连接）
  → 这类似于 try/finally 模式，确保资源被正确释放

Q59：FastAPI Lifespan（生命周期）和传统的 @app.on_event("startup") 有什么区别？
-------------------------------------------------------------------------------
- 你的项目 main.py 中使用 lifespan（asynccontextmanager）管理生命周期
- 传统方式（@app.on_event("startup") / @app.on_event("shutdown")）已被标记为
  弃用（deprecated），lifespan 是推荐的替代方式
- lifespan 的优势：
  → 启动和关闭逻辑写在同一个函数中，代码更集中清晰
  → 可以使用 async with 管理资源（如数据库连接池、模型加载）
  → yield 前后自然区分启动和关闭逻辑
- 你的 lifespan 中执行的操作：
  启动阶段 → init_db() + init_components()（加载 AI 模型）
  关闭阶段 → audio_manager.stop() + video_cap.release()（释放硬件资源）

Q60：FastAPI 的 StreamingResponse 是如何实现视频流传输的？
-------------------------------------------------------------------------------
- 你的项目使用 StreamingResponse 实现 /video_feed 端点的 MJPEG 视频流
- 原理：
  (1) 后端用 OpenCV 逐帧读取摄像头画面
  (2) 在每帧上绘制人脸检测框和情绪标签
  (3) 将帧编码为 JPEG 字节流
  (4) 通过生成器（yield）逐帧输出，设置 Content-Type 为 multipart/x-mixed-replace
- MJPEG 的特点：
  → 本质是连续的 JPEG 图片流，通过 multipart boundary 分隔
  → 前端通过 <img src="/video_feed"> 即可显示（浏览器原生支持）
  → 优点：实现简单，兼容性极好
  → 缺点：无音频、带宽消耗大（每帧都是完整 JPEG）、无法在 <video> 标签播放
- 替代方案（未来升级方向）：
  → WebRTC：真正的实时视频+音频传输
  → HLS/DASH：分段视频流，浏览器 <video> 标签原生支持
  → WebSocket + Canvas：逐帧发送二进制数据到浏览器，Canvas 绘制

追问：MJPEG 流的 HTTP 响应头有哪些关键设置？
  → Content-Type: multipart/x-mixed-replace; boundary=frame
  → Cache-Control: no-cache, no-store（防止缓存）
  → Connection: keep-alive（保持长连接）
  → Pragma: no-cache（兼容旧浏览器）

Q64：SQLite 的事务（Transaction）和 ACID 是怎么保证的？你的项目中有用到事务吗？
-------------------------------------------------------------------------------
- ACID：
  → 原子性（Atomicity）：事务中的操作全做或全不做（回滚机制）
  → 一致性（Consistency）：事务完成后不违反数据库约束（外键、唯一键等）
  → 隔离性（Isolation）：SQLite 默认为 SERIALIZABLE 级别，事务之间互不干扰
  → 持久性（Durability）：已提交的事务即使系统崩溃也不会丢失
- 事务模式（BEGIN 的三种变体）：
  → DEFERRED（默认）：首次读写时才获取锁
  → IMMEDIATE：立即获取 RESERVED 锁，防止写饥饿
  → EXCLUSIVE：立即获取排他锁
- 你的项目：FastAPI + SQLAlchemy/原生 sqlite3，每个 HTTP 请求中的数据库操作
  通常在一个连接中执行；批量写入时可以显式用事务包裹以提高性能
- 追问："如果把 1000 条情绪日志插入数据库，怎么做最快？"
  → 把 1000 条 INSERT 包在一个事务中（BEGIN ... COMMIT），
    有事务 ≈ 0.1 秒，无事务 ≈ 30 秒（差异可达 300 倍！）

Q65：SQLite 的并发性能如何？多用户同时访问你的系统会有问题吗？
-------------------------------------------------------------------------------
- SQLite 使用文件级锁，支持"多读单写"：
  → 同一时间可以有多个读者（SHARED 锁）
  → 但同一时间只能有一个写者（EXCLUSIVE 锁）
- 在你的系统中：
  → 情绪日志写入频率不高（每秒最多一次），并发写入压力很小
  → 多个用户同时查看历史数据（只读）不存在并发问题
  → 但如果有大量 Web 请求同时写数据库，可能出现 SQLITE_BUSY 错误
- 缓解方案：
  → 设置 busy_timeout：PRAGMA busy_timeout = 5000（等 5 秒而不是立即报错）
  → 启用 WAL 模式（Write-Ahead Logging）：读写互不阻塞，并发能力从 10 提升到 100+
    PRAGMA journal_mode = WAL;
  → 如果未来并发需求高，可以升级到 PostgreSQL

Q66：SQLite 的外键约束在你的项目中是怎么生效的？需要注意什么？
-------------------------------------------------------------------------------
- 你的项目数据库设计了 6 张核心表，通过外键关联（如情绪日志表的 user_id → 用户表的 id）
- SQLite 外键约束是支持的，但为了向后兼容，默认关闭！
- 需要在每个数据库连接开始时执行：PRAGMA foreign_keys = ON;
- 不启用的后果：外键定义被解析但不强制执行，可能出现"孤儿记录"
  （如删除了用户但该用户的情绪日志还在）
- 级联操作：ON DELETE CASCADE（删除用户时自动删除关联数据）
- 你的项目 git commit 记录显示：fix: 删除用户时同步清除 SystemEvent 和
  UserHiddenGlobal 关联数据 — 说明你在代码层面做了级联删除处理，即使外键约束
  不开启也能保持数据完整性

Q67：SQLite 的索引（Index）在你项目中有用吗？在哪里？
-------------------------------------------------------------------------------
- 索引可以加速 WHERE、JOIN、ORDER BY 查询，避免全表扫描
- 你的项目中应该建索引的字段：
  → 情绪日志表的 user_id、timestamp（最常按用户和时间查询）
  → 系统事件表的 user_id、timestamp
  → 日记表的 user_id
  → 音乐资源库表的 emotion_tag
- SQLite 默认为主键和 UNIQUE 约束自动建索引
- 如何确认索引是否生效：EXPLAIN QUERY PLAN SELECT ... 查看是否使用索引
- 索引的代价：增删改变慢（需要维护 B+ 树），占用额外存储空间
- 追问："如果查询变慢了，你第一步做什么？" → EXPLAIN QUERY PLAN 看查询计划

Q68：SQLite 的 WAL 模式（Write-Ahead Logging）是什么？为什么推荐开启？
-------------------------------------------------------------------------------
- 默认模式（DELETE/ROLLBACK JOURNAL）：写操作直接修改数据库文件，
  同时维护回滚日志 → 读写互相阻塞
- WAL 模式：
  → 写操作先写到 .wal 文件（追加写入，不阻塞读）
  → 读操作读取的是数据库文件快照，不受写影响
  → 读写几乎完全不阻塞
  → 写入性能提升 40%+
  → 并发能力从约 10 提升到 100+
- 开启方式：PRAGMA journal_mode = WAL;
- 你的项目如果开启 WAL，多个用户同时查看历史和写入情绪日志会更加流畅

Q69：如果数据库文件损坏了怎么办？SQLite 有什么恢复机制？
-------------------------------------------------------------------------------
- 使用 PRAGMA integrity_check; 检查数据库完整性
- 使用 .dump 命令导出所有 SQL → 导入到新数据库（最可靠的恢复方式）
- SQLite 内置备份 API：sqlite3_backup_init() 在线热备份
- WAL 模式增加了抗崩溃能力（崩溃后 WAL 文件中的内容可以重放恢复）
- 预防措施：定期备份 emotisense.db 文件（虽然小但很重要）

Q70：你的系统如何保证用户密码安全？
-------------------------------------------------------------------------------
- 你的用户信息表中存储的是 password_hash（密码哈希），不存储明文密码
- 推荐使用 bcrypt 算法（Python 的 passlib 库或 bcrypt 库）
  → 自动加盐（每个用户独立的随机盐值）
  → 计算成本可调节（cost factor=12 意味着 2^12 次迭代）
  → 抗彩虹表攻击（每用户不同盐值）
- 常见错误回答："我用 MD5 加密了密码" → 这是错误的！
  → MD5 速度快，GPU 可以每秒计算数十亿次 → 易被暴力破解
  → 无盐值 → 相同密码产生相同哈希 → 彩虹表秒破
  → 正确做法：bcrypt / scrypt / Argon2 + 独立盐值 + 高计算成本

Q71：你的系统有 XSS（跨站脚本攻击）风险吗？如何防御？
-------------------------------------------------------------------------------
XSS 防御策略（多层防御，单层不够）：

(1) 输出编码（最基础）：
    → Vue 3 模板中的 {{ }} 插值自动进行 HTML 转义（天然防御）
    → 但 v-html 指令绕过了自动转义，如果内容含用户输入则危险

(2) 在你的系统中的风险点：
    → 日记内容：用户自由输入，如果用 v-html 展示 → 高风险
    → 安慰话术：管理员录入，如果用 v-html 展示 → 中等风险
    → 用户名/标题：用 {{ }} 展示 → 安全
    → 防御：所有用户生成内容用文本插值；管理员录入内容使用 DOMPurify 净化后再用 v-html

(3) CSP（Content Security Policy）响应头：
    → Content-Security-Policy: default-src 'self'; script-src 'self'
    → 即使 XSS 注入成功，恶意脚本也无法执行（浏览器遵从 CSP 策略）
    → 你的 FastAPI 后端可以添加中间件设置 CSP 头

(4) HttpOnly Cookie：
    → Set-Cookie: token=xxx; HttpOnly; Secure; SameSite=Strict
    → JavaScript 无法读取 HttpOnly Cookie，即使用户触发 XSS，token 也不会被窃取

(5) 输入校验：
    → Pydantic 模型对所有输入进行类型和范围校验
    → 对字符串长度、特殊字符进行限制

Q72：你的系统有 CSRF（跨站请求伪造）风险吗？前后端分离下如何防御？
-------------------------------------------------------------------------------
- CSRF 攻击原理：用户登录了你的系统（有有效 Cookie/token），
  同时访问了恶意网站 → 恶意网站向你的系统发起伪造请求（自动携带凭据）
- 你的系统风险分析：
  → 如果使用 Cookie 认证 → 存在 CSRF 风险
  → 如果使用 localStorage + Authorization Header → CSRF 无效
    （因为跨站请求无法自动携带自定义 Header，除非攻击者利用 XSS 先偷 token）
- 防御方案：
  (1) 你的系统用 localStorage 存 token → 天然抗 CSRF（但不是绝对安全，需防 XSS）
  (2) SameSite Cookie：Set-Cookie: SameSite=Strict（浏览器不发送跨站 Cookie）
  (3) CSRF Token：关键操作（删除、修改密码）要求携带随机 token
  (4) Referer/Origin 校验：检查请求来源是否合法
  (5) 二次验证：敏感操作需要重新输入密码

Q73：前后端分离架构下，Token 存在哪里更安全？localStorage vs Cookie？
-------------------------------------------------------------------------------
| 存储方式 | 优点 | 缺点 | XSS 风险 |
|---------|------|------|---------|
| localStorage | 方便，永久存储 | XSS 可窃取 | 高 |
| sessionStorage | 关闭标签页自动清除 | XSS 可窃取 | 高 |
| 内存变量 | JS 闭包保护 | 刷新丢失，需要频繁登录 | 低 |
| HttpOnly Cookie | JS 不可读，防 XSS | 需要防 CSRF | 极低 |
| BFF 模式 | Token 在后端，前段不接触 | 架构复杂 | 极低 |

你的项目使用 localStorage + Authorization Header → 简单易实现，
但 XSS 防御要做好。如果老师追问"为什么不存 Cookie？"，
回答：前后端分离（不同域名/端口）时 Cookie 跨域配置复杂；
且 localStorage 方案与 RESTful API 风格更一致。

Q74：你的系统有哪些常见 Web 安全漏洞需要注意？你做了哪些防护？
-------------------------------------------------------------------------------
你的系统安全检查清单：

| 风险 | 状态 | 你的防护措施 |
|------|------|-------------|
| XSS | 部分防护 | Vue 模板自动转义 + 需注意 v-html 使用 |
| CSRF | 基本安全 | localStorage token（跨站无法自动携带） |
| 密码泄露 | 应确认 | password_hash 存储（需确认是否用 bcrypt） |
| SQL 注入 | 安全 | SQLAlchemy ORM 参数化查询自动防注入 |
| CORS 配置 | 需改进 | allow_origins=["*"] → 生产需改为白名单 |
| 暴力破解 | 未防护 | 登录端点未加频率限制（可加 slowapi） |
